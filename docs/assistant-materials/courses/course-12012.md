## 筛选条件如何驱动列表

来源标识：generated.course.12012.lesson.32121

### 响应式筛选概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Vue 3 的响应式系统会跟踪渲染或计算过程中读取的状态，并在依赖变化时更新结果。筛选页面可把原始课程数组和筛选条件作为事实状态，把可见列表定义为计算结果。这样用户修改关键字、分类或状态时，视图自动更新，无需在多个事件处理器里手工维护第二份列表。

### ref、reactive 与 computed

简单值可用 ref，例如 keyword.value；多个相关筛选字段可用 reactive 对象。computed 接收纯计算函数，读取课程列表和筛选条件，返回过滤后的新数组，并根据依赖缓存。模板会自动解包 ref。原始列表应保留服务端数据，计算属性不要在求值时修改它。watch 更适合执行请求、写存储等副作用，不应拿来替代一个可由状态直接推导的列表。

### 可执行的筛选示例

设 courses 为 ref，filters 包含 keyword 和 category。filteredCourses 先规范化 keyword，再执行 courses.value.filter：标题包含关键字且分类匹配或分类为空。模板用 v-for 渲染 filteredCourses，并为每项提供稳定 course.id 作为 key。若数据来自接口，可对输入做 debounce 后更新请求参数；收到结果时更新原始 courses，界面仍由同一个 computed 推导，避免网络逻辑散落在组件各处。

### 误区与边界

不要直接用数组下标作为会重排列表的 key，否则组件局部状态可能错配。computed 中发请求会因依赖求值时机产生难以预测的副作用。大数据量前端过滤会占用主线程，分页和搜索应交由后端。字符串匹配要明确大小写、空格和本地化规则。解构 reactive 对象的普通属性可能丢失响应性，可保持对象访问或使用 toRefs。筛选为空时也要定义展示全部还是展示空结果。

### 自测与参考答案

自测一：为什么不同时维护 allCourses 和手工更新的 visibleCourses？参考答案：后者容易在某个条件变化时漏同步，computed 可从唯一事实状态稳定推导。自测二：computed 和 watch 的主要差别？答案是 computed 表达无副作用派生值并缓存，watch 用于依赖变化后的副作用。自测三：v-for 为什么用 course.id？答案是稳定身份帮助 Vue 正确复用和移动节点，避免排序筛选后局部状态跟错项目。实践可准备分类、关键字和仅看已购三个条件，逐一组合并手算期望课程编号，再写测试核对 computed 输出。随后改变排序并在卡片输入框中留下内容，验证稳定 key 能让局部状态跟随正确课程。最后把大列表改成服务端分页，说明哪些条件属于请求参数，哪些展示状态仍留在页面。

## 卡片组件如何与页面通信

来源标识：generated.course.12012.lesson.32122

### 组件通信概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Vue 组件常采用单向数据流：父页面通过 props 把课程数据和展示配置传给卡片，卡片通过自定义事件把“收藏”“打开详情”等用户意图上报。父组件拥有业务状态并决定如何更新，子组件专注展示和交互。这种职责分配能让同一卡片在列表、搜索结果和个人中心复用。

### props 与 emits 的契约

在 script setup 中可用 defineProps 声明 course、selected 等输入，并用 TypeScript 类型约束；用 defineEmits 声明 select、favorite 等事件及参数。props 对子组件是只读输入，子组件不应直接修改 course.favorite。点击按钮时 emit('favorite', course.id)，父页面监听事件并调用接口，成功后更新自己的列表。清晰的事件名描述已发生的用户意图，避免让子组件知道父页面的存储实现。

### 课程卡片示例流程

父页面渲染 CourseCard，传入 :course='item'，监听 @open='openCourse' 和 @favorite='toggleFavorite'。卡片标题点击 emit open 并携带 id；收藏按钮先阻止点击冒泡，再 emit favorite。父页面收到 id 后设置该项 loading，调用接口，成功时替换对应课程对象，失败时恢复并提示。若卡片只需支持 v-model 选择状态，可遵循 modelValue 与 update:modelValue 约定。

### 边界与常见误区

事件不会像原生 DOM 事件一样自动穿透多层组件，跨很多层级的共享状态可考虑 provide/inject 或状态管理，但不要为两层通信过早引入全局状态。把整个可变对象交给子组件后修改其内部属性，技术上可能发生，却破坏数据归属并让追踪困难。事件参数应尽量小而稳定，例如传 id 和期望动作；接口错误、权限判断和乐观更新回滚通常由掌握业务上下文的父层负责。

### 自测与参考答案

自测一：卡片是否应直接把 course.favorite 改成 true？参考答案：通常不应，props 由父层拥有，卡片应发出事件让父层更新。自测二：为什么 emits 也要声明类型？答案是让事件名和参数在开发期可检查，并形成组件契约。自测三：按钮位于整卡可点击区域时怎样避免同时打开详情？答案是对按钮点击停止冒泡，再单独上报 favorite 事件，同时保持键盘可访问性和明确的按钮语义。练习可为卡片编写三个组件测试：传入课程后正确展示；点击收藏只发出一次带课程编号的事件；点击收藏不会同时触发打开事件。父页面测试再模拟接口成功和失败，确认状态更新与回滚均由父层完成。最后把卡片放入两个不同页面，若无需知道页面路由和存储细节即可复用，说明组件边界较清晰。
