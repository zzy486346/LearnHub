## 对象在内存里经历什么

来源标识：generated.course.12003.lesson.32031

### 概念入门与课程主题

来源声明：本资料依据课程目录编写，是 AI 生成学习资料，非原授课逐字稿。JVM 负责加载类、执行字节码并管理运行时内存。执行 new 时，虚拟机需要确认类已加载，分配对象内存，将字段设为默认值，设置对象元数据，再执行构造方法。对象通常位于堆中，方法调用产生的栈帧保存局部变量和操作数。垃圾回收关注的是对象是否仍可从一组根引用到达，而不是程序员手动释放。

### 可达性与回收机制

GC Roots 包括活动线程栈中的引用、静态字段引用以及 JVM 内部持有的引用等。收集器从根开始遍历对象图，无法到达的对象成为可回收候选。对象生命周期并不由局部变量离开作用域这一单一事件决定；只要其他可达对象仍持有引用，它就不会被回收。现代收集器通常按区域或分代组织回收，以利用多数对象生命周期较短的经验规律，但具体布局取决于所用收集器。

### 可手推示例

方法 createOrder 中 new 一个 Order，并把它加入静态 List。方法返回后，栈帧消失，但静态 List 仍从 GC Root 指向该 Order，所以对象继续存活。若从 List 删除该元素且没有其他引用，对象才变成不可达候选。可以用小程序循环创建对象，对比“只创建不保存”和“持续加入集合”两种情况下的堆占用，再用受控堆参数观察行为；不要依靠 System.gc() 作为业务释放机制。

### 常见误区与边界

对象不可达不代表立即回收，回收时机由 JVM 决定。把局部变量设为 null 通常不是必要优化，清晰作用域更重要。栈上保存引用并不表示对象本体一定在栈上，逃逸分析可能做优化，但代码不应依赖这种实现细节。finalize 机制不可作为资源管理方案；文件和连接应使用 try-with-resources 明确关闭。内存问题分析要基于实际堆、GC 日志和引用链证据。

### 自测与参考答案

自测一：方法返回后其中创建的对象一定可回收吗？参考答案：不一定，若静态集合或其他可达对象仍引用它就不能回收。自测二：GC 判断的是引用计数吗？参考答案：主流 JVM 以从 GC Roots 出发的可达性分析为基础。自测三：数据库连接能等 GC 自动关闭吗？参考答案：不能，应使用 try-with-resources 或连接池协议及时归还。手推时画出根、引用边和对象，比只背内存区域更有效。

## 内存持续上涨怎么查

来源标识：generated.course.12003.lesson.32032

### 概念入门与课程主题

来源声明：本资料依据课程目录编写，是 AI 生成学习资料，非原授课逐字稿。内存上涨可能是正常缓存预热、流量增长、暂时分配峰值，也可能是对象被意外长期保留。排查目标不是先猜某个类“泄漏”，而是建立时间线：堆已用量是否在完整 GC 后仍抬升，增长与请求或任务是否相关，最终由哪些对象占据空间，以及从 GC Root 到它们的引用链是什么。

### 证据收集机制

先观察进程堆、非堆、GC 次数与暂停、分配速率和容器内存，区分 Java 堆与直接内存等区域。若老年代或 GC 后基线持续上升，在接近问题时获取堆转储，并保留相同时段日志。分析 dominator tree 可找出保留内存大的对象，retained size 表示移除该对象可能释放的连带空间。随后沿 path to GC roots 查明是谁长期持有，而不是只看对象数量。

### 可执行示例

假设课程查询接口把每个不同关键词的完整结果放入静态 Map，且没有容量限制。监控显示每次完整 GC 后基线仍升高。堆转储中 HashMap retained size 最大，键和值数量与不同关键词接近；引用链指向静态 cache 字段。修复可改为有最大容量和过期策略的缓存，并只缓存必要字段。复测同样请求序列，确认缓存大小稳定、GC 后基线不再单调上涨，同时核对命中率和数据库压力。

### 常见误区与边界

看到内存曲线上升就立即手动 GC，可能掩盖模式且不能修复保留链。对象实例多不等于泄漏，短命对象可能很快回收；应关注完整 GC 后的存活量和 retained size。堆转储可能包含用户数据与凭据，采集、传输和保存都要受控。线上获取转储可能造成暂停或磁盘压力，应评估时机和空间。容器 OOM 也可能来自直接内存、线程栈或本地库，不能只看 Java 堆。

### 自测与参考答案

自测一：为什么比较 GC 后基线？参考答案：它更接近仍被长期引用的存活对象量。自测二：shallow size 与 retained size 有何区别？参考答案：前者是对象自身大小，后者包含因它存活而连带保留的对象。自测三：找到大 Map 后下一步是什么？参考答案：沿 GC Root 引用链确认持有者并核对业务用途。修复验收必须重放相同负载，比较堆趋势和功能指标。
