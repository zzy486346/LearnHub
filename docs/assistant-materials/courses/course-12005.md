## 联合索引怎样匹配查询

来源标识：generated.course.12005.lesson.32051

### 概念入门与课程主题

来源声明：本资料依据课程目录编写，是 AI 生成学习资料，非原授课逐字稿。索引是帮助数据库更快定位行的数据结构，同时会增加存储和写入维护成本。联合索引把多个列按固定顺序组织，适合一组稳定的查询模式。本课不从“给每列都建索引”出发，而是先写出真实 WHERE、ORDER BY 和返回范围，再设计能够缩小扫描并尽量利用排序的访问路径。

### 匹配与列顺序机制

以索引 (user_id, status, created_at) 为例，B+Tree 首先按 user_id 排列，同一用户内再按 status，随后按 created_at。查询 user_id=? 可利用最左前缀；同时指定 user_id 和 status 可继续缩小范围；再对 created_at 做范围过滤时也可利用其有序性。若跳过最左列只查 status，通常无法像从首列开始那样高效定位。遇到范围条件后，后续列用于进一步定位的能力会受限制。

### 可手推示例

典型查询为：查某用户已支付订单，限定最近三十天并按创建时间倒序，分页取 20 条。索引 (user_id, status, created_at) 先定位用户与状态的连续区间，再在该区间按时间范围读取，且索引顺序有机会减少额外排序。使用 EXPLAIN 查看实际选择的 key、访问类型、预估 rows 和 Extra；再用具有代表性的数据量执行查询，比较建索引前后的扫描行数与耗时，而不是只看是否出现索引名。

### 常见误区与边界

“最左匹配”不等于 SQL 条件必须按索引列顺序书写，优化器会分析等值条件；关键是索引结构中的列顺序。索引越多写入越慢，重复或前缀重叠索引要审查。对低选择性状态列单独建索引可能收益有限，但放在用户编号之后服务具体组合查询可能合理。函数包裹索引列、隐式类型转换或前导模糊匹配可能影响使用。小表全表扫描也可能是正确选择。

### 自测与参考答案

自测一：该联合索引能否很好支持只按 status 查询全站订单？参考答案：通常不能高效利用首列定位，因为缺少 user_id 条件。自测二：索引设计应先看什么？参考答案：真实高频查询的过滤、排序、返回量和数据分布。自测三：EXPLAIN 显示用了索引就一定快吗？参考答案：不一定，还要看扫描行数、回表、排序、实际耗时与并发负载。优化后应验证写入成本和其他查询没有明显退化。

## 执行计划告诉了什么

来源标识：generated.course.12005.lesson.32052

### 课程概览与来源说明

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。本课介绍 MySQL 执行计划：它是优化器为一条查询选出的访问路径说明，能展示表的读取顺序、候选索引、实际选用索引、访问方式、预计扫描行数和额外动作。阅读执行计划的目的，是用证据判断查询为何慢，而不是看到某个字段就立即加索引。

### 关键字段怎样配合阅读

使用 EXPLAIN SELECT ... 可获得计划。type 表示访问方式，常见的 const、ref、range 通常比全表扫描 ALL 更有选择性，但仍要结合数据量判断；possible_keys 是可选索引，key 是最终采用的索引；key_len 反映索引参与匹配的大致长度；rows 是优化器估算的扫描量，不是精确计数；Extra 中 Using filesort、Using temporary 等提示还存在排序或临时表工作。

### 可手推的订单查询示例

假设订单表有联合索引 idx_user_status_created(user_id,status,created_at)，查询条件是 user_id=7、status='PAID'，再按 created_at 范围过滤。执行计划若显示 key=idx_user_status_created、type=range、rows=20，说明优化器可从前导等值列进入索引，再扫描有限日期范围。若只查 status 而计划为 ALL，是因为跳过了联合索引最左列，不能仅凭“索引存在”认定它会生效。

### 常见误区与验证边界

type=ALL 不必然是故障：小表全扫可能比随机回表更便宜；rows 只是统计信息推算，数据分布变化后可能失真；出现 Using filesort 也不等于在磁盘排序，它表示不能直接利用索引顺序完成排序。优化应同时观察真实耗时、返回行数、数据分布和慢查询记录。修改索引后要重新 EXPLAIN，并在近似真实数据量上比较，避免用开发库几行数据下结论。

### 自测与参考答案

自测一：possible_keys 有值而 key 为空意味着什么？参考答案：优化器知道存在候选索引，但估算后选择了其他路径，需检查选择性、统计信息与数据规模。自测二：rows 从十万降到一百能否证明优化完成？参考答案：说明预计扫描量显著下降，是积极信号，但还要看实际耗时、回表次数、排序和锁等待。自测三：为什么先执行 EXPLAIN 再加索引？答案是先找出真正的访问路径和瓶颈，减少猜测式冗余索引。练习时可准备三组不同分布的数据：用户高度集中、状态几乎相同、日期范围极宽，分别观察优化器选择。再把查询实际返回行数与估算行数记录在表格中；若相差很大，更新统计信息后重试。最后比较新增索引前后的写入成本和磁盘占用，说明索引优化是读写与空间的综合权衡，并为保留或删除索引留下数据依据。
