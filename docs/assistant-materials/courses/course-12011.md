## 一次提交应该装什么

来源标识：generated.course.12011.lesson.32111

### 提交设计概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Git 提交是一次有作者、时间、说明和父节点的项目快照。高质量提交围绕一个可解释的目标组织，例如“修复取消订单后库存未释放”，并同时包含让该目标成立的代码和必要测试。提交粒度应便于评审、定位和回退，而不是机械追求文件越少越好。

### 原子提交的判断标准

一个提交应在自身范围内逻辑完整：构建不应因半成品失败，行为改变应有相应验证，重构和功能若能独立说明就分开。检查 git diff 和暂存区，确认没有调试日志、生成文件、密钥和无关格式化。提交信息说明做了什么以及必要的原因，标题使用仓库约定的格式。若一个提交说明中必须频繁使用“顺便”，通常表示应拆分。

### 拆分一个混合改动

假设工作区同时有库存修复、IDE 格式化和 README 更新。先用 git diff 查看各块，按路径或补丁块暂存库存代码与测试，运行验证后提交 fix: 修复取消订单库存释放；再单独处理文档。若同一文件含两类改动，可交互式选择补丁块，但暂存后必须看 git diff --cached，防止拆分导致变量引用或测试缺失。每个提交都应能独立解释其价值。

### 边界与误区

原子提交不等于每一行一个提交，也不要求把不可分割的数据库迁移和代码强拆。把大批格式化混入行为修复会增加评审噪声。不要用提交历史保存密钥，即使后续删除，旧对象中仍可能存在。已共享分支上的历史重写会影响协作者，回退公开错误通常用 revert 新增反向提交；个人分支整理历史则需先确认协作边界。

### 自测与参考答案

自测一：修复代码与证明修复的测试应分两个提交吗？参考答案：通常可放在同一原子提交，因为它们共同表达一个行为目标。自测二：为何提交前看 cached diff？答案是最终提交内容由暂存区决定，它可能不同于整个工作区。自测三：一个提交同时升级依赖、重命名目录并新增功能有何问题？答案是评审和回退难以区分风险，应在依赖允许时拆成独立、可验证步骤。练习时创建包含功能修改、调试输出和文档拼写的工作区，先写一句提交目标，再只暂存实现该目标所需的补丁块。检查暂存差异并运行目标测试后提交，剩余改动另行处理。随后尝试单独回退该提交，确认项目仍可构建且只撤销预期行为。若回退牵连无关功能，说明原提交边界仍需调整。

## 冲突怎样安全解决

来源标识：generated.course.12011.lesson.32112

### 合并冲突概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Git 能自动合并不同区域的变化，但双方修改同一上下文、一个删除而另一个修改，或重命名关系不明确时，需要人决定最终内容。冲突并不表示某一方一定错误，它表示 Git 缺少业务语义。安全解决的核心是理解共同祖先、当前分支和待合并分支各自意图。

### 冲突标记和状态

合并冲突文件会出现当前版本、分隔线和另一版本标记。先用 git status 查看未合并路径，再对照共同祖先和双方提交说明。不能简单保留全部文本，因为两段代码可能重复调用或违反新接口；也不能一律选择 ours 或 theirs，因为这些词在 merge、rebase 等场景的语义容易混淆。编辑到正确最终形态后移除标记，暂存文件表示该路径已解决。

### 安全解决的实际步骤

例如一方把 calculatePrice 增加 currency 参数，另一方增加优惠券逻辑。正确结果通常需要让优惠逻辑调用新签名，并同步测试，而不是任选一边。步骤是暂停其他改动、查看双方 diff 和调用点、编辑整合、搜索残留冲突标记、运行目标测试和构建、查看最终 diff，最后完成 merge 或继续 rebase。若判断错误，可在未完成阶段使用对应 abort 命令回到操作前状态。

### 边界与常见误区

解决文本冲突不代表语义正确：两个文件各自自动合并，也可能共同造成重复注册或顺序错误。锁文件可由包管理器按确定流程重建，但不能随意删除依赖变更。二进制文件无法像文本一样手工合并，需要确认应保留哪个版本或重新生成。不要在冲突处理中顺便大规模重构，这会模糊原始差异；必要重构应在合并完成并验证后单独提交。

### 自测与参考答案

自测一：删除冲突标记并成功提交能证明解决正确吗？参考答案：不能，还需编译、测试并检查业务语义。自测二：为什么要看共同祖先？答案是它揭示双方分别从什么基线改变，帮助识别各自意图。自测三：冲突太复杂且方向错误怎么办？答案是在尚未完成时使用 merge --abort 或 rebase --abort 恢复操作前状态，重新沟通和拆解，而不是强行提交不可理解的结果。练习可从同一基线建立两个分支，一边修改函数签名，另一边新增调用逻辑，再主动合并。解决前分别查看祖先、当前版本和对方版本，写下两边的行为目标。整合后除了搜索冲突标记，还要运行调用链测试并阅读最终差异。最后重新做一次错误合并并使用中止命令恢复，确认中止与回滚已完成合并的区别。
