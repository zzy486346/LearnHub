## 镜像如何封装应用

来源标识：generated.course.12009.lesson.32091

### 镜像与容器概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Docker 镜像是只读分层的应用交付物，通常包含运行时、程序文件、依赖和默认启动指令；容器是镜像的一个运行实例，额外带可写层、进程、网络与资源限制。镜像让测试和部署使用同一组文件，但宿主机内核、外部配置与持久化数据仍在镜像之外。

### Dockerfile 和分层机制

Dockerfile 以 FROM 选择基础镜像，WORKDIR 设置工作目录，COPY 放入构建产物，RUN 在构建时安装或处理文件，ENTRYPOINT、CMD 定义运行时入口和默认参数。每个会改变文件系统的步骤可能形成层，层可复用缓存。稳定依赖应放在变化频率低的前面，源代码放后面，以减少无关改动导致的重建。基础镜像最好固定明确版本或摘要，降低环境漂移。

### Java 应用构建示例

可先在构建阶段使用 JDK 编译，再把生成的 jar 复制到仅含 JRE 的运行阶段：第一阶段执行 Maven package，第二阶段 FROM eclipse-temurin:17-jre，COPY --from=build /app/target/app.jar /app/app.jar，ENTRYPOINT 执行 java -jar。多阶段构建避免把 Maven 缓存和源码放入最终镜像。配合 .dockerignore 排除 target、.git、日志和本地密钥，可缩小上下文和泄露面。

### 常见误区与安全边界

镜像可重复不等于构建绝对可复现：浮动标签、在线依赖变化和构建时间都可能改变结果。不要用 COPY . . 无选择地打包工作区，更不能把 .env 或密钥烘进镜像；敏感配置应在运行时注入。容器删除后可写层数据会丢失，数据库必须使用卷或外部存储。镜像内尽量使用非 root 用户，并扫描基础镜像漏洞，但扫描通过也不代表运行时配置安全。

### 自测与参考答案

自测一：镜像和容器是什么关系？参考答案：镜像是只读模板，容器是其运行实例并带可写状态。自测二：多阶段构建为什么能减小 Java 镜像？答案是编译工具和中间产物留在构建阶段，最终阶段只复制运行所需文件。自测三：修改一行源码为何可能只重跑后几层？答案是前面指令及输入未变时可复用层缓存；若过早复制整个项目，则无关文件变化也会使后续缓存失效。练习时先构建包含编译工具的单阶段镜像，再改为多阶段，比较镜像大小、层清单和启动结果。随后只修改业务源码与只修改依赖清单，分别观察缓存命中层。还应检查镜像历史和容器环境中是否出现本地密钥，并以普通用户启动后访问健康接口。通过这些证据验证交付物既能运行，也没有把构建环境和敏感配置带入。

## 多个服务怎样一起启动

来源标识：generated.course.12009.lesson.32092

### Compose 课程概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Docker Compose 用一个声明式 YAML 文件描述一组相关容器，包括服务镜像或构建方式、环境变量、网络、卷、端口、健康检查和依赖关系。它适合在本地或单机环境复现应用拓扑，使团队用一致命令启动 API、MySQL、Redis 等组件，并集中查看状态和日志。

### 服务发现和数据持久化

同一 Compose 网络中的服务可通过服务名解析，例如后端连接 mysql:3306，而不是容器内的 localhost；localhost 指当前容器自身。ports 把宿主端口映射到容器端口，只有宿主或外部需要访问时才必需。数据库目录用具名卷挂载，容器重建后数据仍在。环境变量可以引用 .env，但只有 Compose 文件显式引用或 env_file 注入的变量才会进入容器。

### 三服务拓扑示例

设 services 包含 api、mysql、redis。api 的 DATABASE_URL 指向 mysql，REDIS_HOST 指向 redis；mysql 挂载 db-data 卷并配置健康检查；api 可 depends_on mysql 的 service_healthy 条件，减少数据库尚未就绪时立即启动失败。执行 docker compose up -d --wait 后检查 docker compose ps；若 api 异常，再看该服务日志和健康状态。配置变更后可定向重建 api，不必删除数据卷。

### 启动顺序的边界

depends_on 只能表达容器级依赖，普通启动完成不表示应用真正可用；健康检查应验证服务能力，业务程序自身也需要连接重试。Compose 不会自动执行所有数据库迁移，除非明确配置迁移任务。不要把生产密钥写入 YAML 或提交的 .env。docker compose down 与 down -v 含义不同，后者会删除卷并可能造成数据丢失。多个项目若显式使用相同 project name，还可能发生资源命名冲突。

### 自测与参考答案

自测一：api 容器连接 MySQL 为什么不能填 localhost？参考答案：容器中的 localhost 指 api 自己，应使用同网络的服务名 mysql。自测二：depends_on 能保证表迁移已完成吗？答案不能，除非把迁移建模为有完成条件的任务；应用仍需处理就绪与重试。自测三：重建数据库容器怎样保留数据？答案是把数据库目录挂到具名卷，并避免执行带 -v 的删除命令。端口映射服务于宿主访问，不是容器互联的前提。实践可先启动完整拓扑，记录每个服务的网络别名、健康状态和卷名；再只停止数据库并观察应用的重连行为。数据库恢复后确认应用无需重建即可继续服务。然后重建数据库容器并核对原数据仍在，最后修改一个非敏感环境变量定向重建应用。整个过程不要删除卷，由此区分容器生命周期、服务就绪和数据生命周期。还要记录实际使用的项目名。
