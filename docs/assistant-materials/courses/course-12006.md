### Redis 位图课程概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Redis 是内存键值数据库，Bitmap 并非独立数据类型，而是把字符串值按二进制位操作。每个位只表示零或一，非常适合签到、是否活跃、是否完成等真假状态。相比为每一天保存完整对象，按位记录能显著减少空间，并能利用 Redis 命令完成计数和位运算。

### 键和偏移量的设计

可按月建立键 sign:{userId}:2026-10，把当月第几天映射为从零开始的偏移量，例如 1 日对应 offset 0，20 日对应 offset 19。签到时执行 SETBIT key offset 1，查询某天用 GETBIT，统计本月签到天数用 BITCOUNT。按用户和月份拆键既限制单个值大小，也方便设置过期时间。花括号还能在 Redis Cluster 中让同一用户相关键落到同一哈希槽。

### 可执行的签到示例

用户 42 在 1、2、5 日签到，可依次执行 SETBIT sign:{42}:2026-10 0 1、SETBIT ... 1 1、SETBIT ... 4 1。BITCOUNT 返回 3。检查 3 日时 GETBIT offset 2 返回 0。若要计算从月初到今天连续签到，可取出相应位段后从当天向前逐位判断，遇到零停止；业务代码必须统一字节序、位序和日期到偏移量的规则，并用测试固定月初、月末和闰日边界。

### 边界与常见误区

Bitmap 适合稠密的布尔状态，不适合直接保存签到时间、设备或补签原因等多字段信息，这些详情应另存。SETBIT 会扩展字符串，若第一次写入极大的 offset，可能分配较大空间并带来延迟，因此偏移量必须受控。BITCOUNT 统计的是一的数量，不会自动判断连续天数。按月切键后跨月连续签到需要业务层合并判断，时区也应固定，否则午夜附近可能落入错误日期。

### 自测与参考答案

自测一：为什么 1 日通常映射到 offset 0？参考答案：Redis 位偏移从零开始，这样日期 d 可直接映射为 d-1。自测二：某月键 BITCOUNT 为 18 说明什么？答案是该位图中共有 18 个置一位，若写入规则正确，可解释为签到 18 天，但不能说明连续签到 18 天。自测三：需要记录补签原因怎么办？答案是 Bitmap 继续承担真假状态，原因放入关系表或哈希等结构，通过用户和日期关联。实践时可为二月、三十天月份和三十一天月份分别写测试，验证最后一天不会越界。再模拟用户跨时区旅行，确认业务按账号时区还是服务器时区计算日期。若产品允许补签，应验证重复补签仍只保留一个置一位，并让详情记录保持幂等。最后估算十万用户一年位图的空间，与逐日行记录比较，理解紧凑存储带来的收益和信息损失。

## 积分排行榜如何更新

### 有序集合课程概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。Redis Sorted Set 由唯一成员 member 和可排序的浮点分值 score 组成，适合积分榜、热度榜和延迟任务。成员不会重复，更新同一成员会改变分值；Redis 按 score 排序，并在同分时按成员的字典序确定稳定次序，因此它能同时完成去重、更新和名次读取。

### 更新和读取机制

ZADD board 120 user:7 可设置积分，ZINCRBY board 5 user:7 可在原分数上增加五分。默认升序排名用 ZRANK，高分在前常用 ZREVRANK；ZRANGE 或 ZREVRANGE 配合 WITHSCORES 可读取区间及分数。排名从零开始，页面展示时通常加一。查询单人积分用 ZSCORE。若积分变动来自多次业务事件，应先保证事件幂等，避免同一奖励重复执行 ZINCRBY。

### 可手推的排行榜例子

初始执行 ZADD points 80 user:1 100 user:2 90 user:3，高到低是 user:2、user:3、user:1。user:1 完成任务获得 25 分，ZINCRBY 后变为 105，ZREVRANK points user:1 返回 0，表示第一名。读取前三名可用 ZREVRANGE points 0 2 WITHSCORES。若 user:4 也是 105，同分的先后由成员字典序决定；若业务要求按最早达到分数者优先，必须另行编码时间或设计复合排序方案。

### 误区、精度与规模边界

Sorted Set 的 score 使用双精度浮点数，超大整数或高精度货币不应无条件直接作为 score；积分可限制在安全整数范围。排行榜只保存当前结果，不天然保留每次加分流水，审计需要数据库事实表。删除过期榜单成员可用 ZREM 或按分数区间清理。大型榜单分页越靠后读取成本和传输量越大，可优先提供前 N 名与用户附近排名，而不是让客户端一次拉取全榜。

### 自测与参考答案

自测一：ZREVRANK 返回 0 是第几名？参考答案：内部零基排名为 0，展示为第一名。自测二：重复消费一次“加 10 分”消息会怎样？答案是若直接再次 ZINCRBY，积分会多加十，因此消费者需按业务事件编号去重。自测三：两个成员 score 相同是否没有顺序？答案是否定的，Redis 会按成员字典序确定顺序，但这种顺序未必符合业务的同分规则，需要显式设计。练习可准备五名用户并逐次加分，每步手算名次，再与命令结果核对。随后故意重放一个奖励事件，观察没有幂等保护时的错误，再增加事件表修复。还可设计日榜和总榜两个键，说明日榜何时过期、总榜如何保留，并验证跨天更新不会写错键。最后讨论撤销奖励时的负增量以及积分不得低于零的业务约束应由哪一层保证。再为同分用户制定明确规则，并用测试确认成员字典序与产品要求是否一致；若不一致，就在上线前调整建模。
