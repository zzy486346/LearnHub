## 订单表如何表达事实

来源标识：generated.course.12004.lesson.32041

### 概念入门与课程主题

来源声明：本资料依据课程目录编写，是 AI 生成学习资料，非原授课逐字稿。关系表用列、行、约束和关系记录业务事实。订单表的一行代表一笔具有稳定身份的订单，字段应回答谁购买、购买什么、金额多少、当前状态及何时创建。设计重点是选择清晰类型并让数据库约束守住基本不变量，而不是把所有信息塞进一个文本字段。本课从订单事实理解主键、唯一键、非空和关联关系。

### 字段与约束机制

订单可使用数据库主键 id 作为内部标识，另设 order_no 作为对外业务号并添加唯一约束。user_id、status、total_amount、created_at 等关键字段通常非空。金额使用 DECIMAL 保存十进制定点值，并明确币种或系统仅支持的币种。订单项放在 order_item 表，通过 order_id 关联订单，一行表达一个商品快照、数量和成交单价。商品名称与价格可保存下单时快照，避免商品后续修改改变历史事实。

### 可执行示例

建立 orders(id BIGINT 主键, order_no VARCHAR 唯一, user_id BIGINT 非空, status VARCHAR 非空, total_amount DECIMAL(12,2) 非空, created_at DATETIME 非空)。order_item 包含 id、order_id、product_id、product_name、unit_price 和 quantity。订单总额可由各项 unit_price×quantity 汇总后写入，并在应用层验证非负。插入相同 order_no 两次时，唯一约束应拒绝第二次，从而为请求幂等提供最后一道保护。

### 常见误区与边界

不要使用 FLOAT 或 DOUBLE 存储需要精确结算的金额。只在 Java 校验非空而数据库允许 NULL，会让其他写入通道产生脏数据。外键是否启用要结合团队运维与写入模式选择，但即使不用物理外键，应用也必须维护关系并有孤儿数据检查。状态字段不应随意写任意字符串，可使用受控枚举和状态转换规则。删除用户或商品时不能简单级联删除历史订单事实。

## 转账为什么需要事务

来源标识：generated.course.12004.lesson.32042

### 概念入门与课程主题

来源声明：本资料依据课程目录编写，是 AI 生成学习资料，非原授课逐字稿。转账包含至少两个相关写操作：付款账户减少余额，收款账户增加余额。若前一步成功而后一步失败，系统总金额就不再守恒。事务把一组操作定义为共同提交或共同回滚的工作单元。本课通过转账理解原子性、一致性、隔离性和持久性，并区分异常回滚与并发竞争两类问题。

### 事务与锁机制

事务开始后，SQL 修改先属于当前事务，全部成功才 commit；发生符合回滚规则的异常则 rollback。原子性解决半完成，隔离性约束并发事务之间可见与影响的方式。转账还要防止两个请求同时基于旧余额扣款，可使用 SELECT ... FOR UPDATE 锁定账户行，或使用带余额条件的原子 UPDATE。为降低死锁，涉及多个账户时应按稳定顺序获取锁，并让事务范围尽量短。

### 可执行与可手推示例

A 余额 100，B 余额 20，转账 30。事务内先按账户编号顺序锁定 A、B，检查 A 余额足够，执行 A=A-30、B=B+30，并写转账流水，最后提交；结果是 70 与 50。若写 B 时发生异常，整个事务回滚，余额恢复为 100 与 20。测试应主动在第二步抛异常验证回滚，再并发提交两笔从 A 扣 80 的请求，确认最多一笔成功且余额不为负。

### 常见误区与边界

仅给方法加事务注解不代表任何异常都会回滚，要理解代理调用方式和回滚规则；同类内部调用可能绕过代理。长事务中执行远程 HTTP 会长时间占锁，应把外部交互设计为事务外流程或可靠事件。数据库事务只覆盖同一资源管理器，无法自动让消息、缓存和外部支付共同原子提交。隔离级别越高也不是越好，需要在一致性、冲突和吞吐之间选择。

### 自测与参考答案

自测一：事务回滚解决什么？参考答案：某一步失败时撤销同一事务已完成的写入，避免半完成。自测二：回滚能自动避免两个并发扣款吗？参考答案：不能，还需锁、条件更新或合适隔离策略。自测三：为什么按账户编号排序加锁？参考答案：减少不同事务以相反顺序等待造成死锁的机会。验收要覆盖正常提交、异常回滚、余额不足、重复请求和并发竞争。
