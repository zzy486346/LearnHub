## 订单消息如何到达消费者

来源标识：generated.course.12008.lesson.32081

### RabbitMQ 路由概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。RabbitMQ 通过生产者、交换机、绑定、队列和消费者协作传递消息。生产者通常把订单事件发布给交换机，而不是直接指定消费者；交换机根据自身类型、routing key 和绑定规则把消息路由到一个或多个队列；消费者从队列获取消息并处理。队列承担缓冲，使发布速度和消费速度可以不同。

### 交换机类型与绑定

direct 交换机按 routing key 精确匹配绑定键，适合 order.paid 等明确事件；topic 交换机用点分词和星号、井号通配，适合 order.* 或 order.#；fanout 忽略 routing key，把消息广播给所有绑定队列。队列是否持久化、消息是否标记持久化以及交换机是否持久化是不同配置。发布成功也不等于业务已消费，需要发布确认、路由返回和消费确认共同建立可观测链路。

### 订单已支付的传递示例

支付服务生成事件 eventId=e-101、orderId=42，发布到 exchange=order.events，routingKey=order.paid。库存队列以 order.paid 绑定，积分队列可用 order.* 绑定，于是同一事件进入两个独立队列，各消费者按自己的速度处理。若 routing key 没有任何绑定匹配，消息可能不可达；生产者应启用 mandatory 返回或配置备用交换机，并记录事件编号用于排查。

### 可靠性边界与误区

消息持久化减少代理重启丢失风险，但不能单独保证端到端业务完成。生产者确认说明代理接收了消息，不代表消费者事务成功；消费者确认应在本地业务提交之后发送。网络断开可能使发送方不知道代理是否接收，因而重试会产生重复消息。队列堆积不是简单增加消费者就一定解决，还要检查下游数据库、预取数量、单条耗时和失败重试风暴。

### 自测与参考答案

自测一：生产者将消息发到交换机后，谁决定进入哪个队列？参考答案：交换机依据类型、routing key 与绑定规则决定。自测二：publisher confirm 成功能证明订单积分已增加吗？答案不能，它只证明消息被代理接收，消费端业务结果还需单独确认。自测三：库存和积分都要处理支付事件怎样设计？答案是为两个业务分别建立队列并绑定同一事件，避免多个业务消费者竞争同一队列而只让其中一个收到。可再画出发布确认、路由、入队、投递、业务提交和消费确认六个节点，为每个节点标出可观测指标。随后故意把 routing key 写错，验证 mandatory 返回如何暴露不可路由消息；再停止一个消费者，观察对应队列积压而其他队列仍正常。这个练习说明广播业务要依赖独立队列，也能区分代理接收成功与最终处理成功。

## 重复消息如何安全处理

来源标识：generated.course.12008.lesson.32082

### 重复投递课程概览

本资料依据课程目录编写，是 AI 生成的学习资料，非原授课逐字稿。可靠消息系统通常选择至少一次投递：只要确认状态不确定，就可能再次投递，以降低丢消息概率。消费者完成数据库写入后若在发送 ack 前断线，代理看不到确认，会把消息重新交付；生产者确认超时后重发，也可能让内容重复。因此业务消费者必须把重复视为正常输入，而非偶发现象。

### 确认和重投机制

消费者收到消息后先校验，再执行本地事务，事务成功才 ack。处理失败可根据原因决定重新入队、有限次数重试或进入死信队列。若先 ack 后写库，进程在两者之间崩溃会永久丢失业务动作；若先写库后 ack，则可能重复，所以需要幂等。redelivered 标记可辅助观察，但不能作为唯一去重依据，因为生产者重发生成的新投递未必带该标记。

### 订单事件幂等示例

事件携带稳定 eventId=e-101。消费者在同一数据库事务中先插入 processed_event(event_id,consumer_name)，表上建立唯一约束；插入成功才更新积分。重复事件插入违反唯一约束时，消费者确认消息但不再次加分。也可利用订单状态机进行条件更新，例如 UPDATE ... SET status='PAID' WHERE id=42 AND status='PENDING'，受影响行数为零时说明无需重复迁移。

### 误区与工程边界

仅在进程内 Set 记录消息编号无法跨重启、跨实例去重；Redis SETNX 可用于部分场景，但若去重标记与数据库业务写入不是同一事务，仍存在标记成功而业务失败的窗口。所有消息永久去重会无限增长，应按业务允许的重放期限归档或清理。幂等键必须稳定且对应业务动作，随机生成新的消费编号没有作用。死信不是问题终点，必须有告警、查看与重放流程。

### 自测与参考答案

自测一：数据库提交成功但 ack 未到代理会怎样？参考答案：消息可能重新投递，所以消费者要幂等。自测二：为什么不能只看 redelivered 判断重复？答案是生产者重发或跨链路复制也可能形成语义重复，稳定业务事件编号更可靠。自测三：先写去重表再更新积分应否同事务？答案应当同事务，否则两步之间故障会出现已去重却未完成业务的永久遗漏。确认与幂等共同提供可靠边界。实践可在业务提交后、发送确认前主动终止消费者，再启动它观察重复投递。检查积分仍只增加一次、去重表只有一行且消息最终确认。然后制造永久格式错误，验证它经过有限重试进入死信队列而非无限循环。最后演练修正数据后的人工重放，确保重放也沿用原事件编号并留下审计记录。
