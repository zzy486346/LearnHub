## 实时搜索为何会结果倒退

来源标识：generated.course.12014.lesson.32141

### 从实时搜索认识请求竞态

依据课程目录编写的AI生成学习资料，非原授课逐字稿。实时搜索会在用户每输入几个字符时发送请求，例如依次搜索“r”“re”“redis”。网络响应顺序并不保证与发送顺序一致：查询“redis”的新请求可能先完成，查询“re”的旧请求随后才返回。如果页面见到响应就直接覆盖列表，用户最终看到的反而是较旧、范围更宽的结果，这就是结果倒退。课程主题关注前端如何识别异步完成顺序与用户最新意图之间的差异，并让界面只接受仍然有效的结果。

### 竞态形成的机制

浏览器可以同时保留多个未完成请求，每个 Promise 独立进入完成回调。发送先后、服务端处理耗时、缓存命中和网络抖动都会改变响应先后。变量 keyword 即使已经更新，旧回调仍携带旧查询对应的数据；若回调仅执行 result.value = response.data，它无法判断自己是否过期。防抖只能减少请求数量，不能从逻辑上保证响应有序，因为两个实际发出的请求仍可能乱序。节流同样不等于取消旧任务，必须另外建立“本次响应是否属于最新意图”的判定。

### 用序号或取消信号解决

一种可手推方案是维护递增序号。发送“re”时得到序号 7，发送“redis”时得到序号 8；响应回调只在自己的序号等于 currentRequestId 时更新页面。即使 7 最后返回，也会因 7 不等于 8 被丢弃。另一种方案使用 AbortController：新搜索开始前调用上一次控制器的 abort，再把新 signal 交给 fetch。取消能节约客户端后续处理，但请求可能已到达服务端，因此服务端不能把取消当作业务事务必然回滚。序号校验仍是保护最终展示状态的简单手段。

### 常见误区与状态边界

不要用“最后返回的就是最新请求”作为假设，也不要只根据输入框当前文本去猜响应归属，因为不同参数可能规范化为相同文本。加载状态也要与活动请求绑定：旧请求结束时不应把新请求的 loading 关闭。错误提示同理，已过期请求的超时不应覆盖新请求的成功结果。对于分页搜索，还要把关键词、页码、筛选项共同组成请求身份。取消异常应与真正的网络失败区分，避免用户主动继续输入时页面弹出无意义的失败提示。

### 自测与参考答案

自测一：先请求 A，后请求 B，B 先成功而 A 后成功，页面应展示谁？参考答案：展示 B，因为它代表最新意图，A 的响应应被忽略。自测二：加了 300 毫秒防抖是否一定没有竞态？参考答案：不一定，只要仍有两个请求真正发出就可能乱序。自测三：AbortController 是否保证服务端没执行旧请求？参考答案：不能，它主要取消客户端等待和处理，服务端可能已经收到请求。工程验收应模拟可控延迟，证明旧响应无法覆盖新结果，并检查 loading 与错误状态也不会倒退。

## 登录失效怎样统一处理

来源标识：generated.course.12014.lesson.32142

### 登录失效处理的目标

依据课程目录编写的AI生成学习资料，非原授课逐字稿。登录失效可能表现为访问令牌过期、会话被撤销、刷新令牌不可用，或后端明确返回未认证状态。若每个页面自己写跳转逻辑，提示文案、清理范围和返回地址会不一致；多个并发请求还可能同时弹窗和跳转。统一处理的目标是在网络请求边界识别认证失败，集中清理客户端认证状态，选择刷新或重新登录，并保留安全的原访问位置，让业务组件只处理自己的业务成功与失败。

### 拦截器与状态机机制

常见做法是在 HTTP 客户端响应拦截器中检查状态码和业务错误码。首次发现可刷新错误时，把会话状态从 authenticated 切到 refreshing，并启动唯一刷新请求；刷新期间到达的其他失败请求进入等待队列，而不是各自刷新。刷新成功后更新凭证并按原配置重放等待请求；刷新失败则进入 anonymous 状态，统一清理凭证并跳转登录页。若系统采用 HttpOnly Cookie，前端不能读取令牌，但仍可用相同状态机协调重试和跳转。

### 并发失效的可执行示例

假设课程详情、学习进度和通知三个请求同时返回 401。第一个响应取得 refreshPromise 并调用刷新接口，后两个响应复用同一个 Promise。刷新成功后，三者各重放一次；要在请求配置上标记 _retried，避免新凭证仍无效时无限循环。若刷新失败，只触发一次 logoutAndRedirect，并用 encodeURIComponent 保存站内返回路径。登录成功后先校验返回地址是本站允许路由，再恢复访问，不能直接信任任意外部 URL，以免形成开放重定向。

### 错误分类与安全边界

401 通常表示没有有效认证，403 通常表示身份已确认但权限不足，两者不应都跳登录页。业务接口返回“课程不可访问”时，应展示授权结果而不是反复刷新令牌。刷新接口自身必须绕过普通重试拦截器，否则可能递归调用。非幂等写请求是否自动重放要谨慎：如果服务端可能已完成写入而响应丢失，盲目重放会重复操作，应依靠幂等键或让用户确认。退出时还应清理内存用户信息、缓存查询和敏感页面状态，但不要误删与登录无关的本地偏好。

### 自测与参考答案

自测一：五个请求同时 401，应发送几次刷新请求？参考答案：同一失效窗口内通常一次，其余请求等待共同结果。自测二：收到 403 是否应清除登录状态？参考答案：通常不应，403 是当前身份没有目标资源权限，应展示权限错误。自测三：刷新成功后所有 POST 都能无条件重放吗？参考答案：不能，需确认请求具有幂等保障且未造成重复副作用。测试时应覆盖刷新成功、刷新失败、刷新接口也失效、并发只刷新一次、重放最多一次以及安全返回地址六类情况。
