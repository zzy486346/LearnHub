## 倒排索引怎样找到课程

来源标识：generated.course.12015.lesson.32151

### 从课程搜索认识倒排索引

依据课程目录编写的AI生成学习资料，非原授课逐字稿。普通逐条扫描需要检查每门课程正文是否含查询词，数据越多越慢。倒排索引把方向反过来：先为每个词项保存出现过它的文档清单，搜索时从词项直接定位候选课程。比如课程 A 是“Redis 缓存治理”，课程 B 是“MySQL 索引入门”；分析后词项 redis 指向 A，索引指向 B。用户搜索 Redis 时不必重新阅读所有课程，只需查词典并取得对应文档编号。

### 分析链如何产生词项

文本进入索引前通常经过字符过滤、分词和词项过滤。分词器决定边界，过滤器可统一大小写、去除部分停用词或生成同义表达。字段 mapping 中的 analyzer 用于建索引，search_analyzer 用于查询；两边规则若不协调，文档里的词与查询词可能无法相遇。keyword 字段通常把整个值当成一个词项，适合状态码、精确标签和聚合；text 字段适合全文检索。原始文本仍保存在 _source，而倒排结构服务于定位与评分。

### 手推一次检索过程

有三篇文档：D1“Redis 缓存”，D2“Redis Lua”，D3“MySQL 索引”。简化分词后，redis 的发布列表是 [D1,D2]，缓存是 [D1]，lua 是 [D2]。查询“Redis Lua”被分析成 redis 和 lua，布尔 must 要求同时出现时只剩 D2；should 可以让 D1 也成为候选，但 D2 匹配更多词通常得分更高。真实倒排记录还可能保存词频、位置和字段长度，用于短语匹配、高亮和相关性计算。检索得到的是候选文档编号，再读取存储字段组成结果。

### 映射误区与更新边界

倒排索引不是数据库 B 树的简单同义词，也不是把整段文本原样作为键。修改 analyzer 往往需要新建索引并重建数据，因为旧词项不会自动按新规则重算。中文如果使用不合适的分词规则，可能把课程名切得过细或完全不切，导致召回异常。刷新使新文档可被搜索，但不等同于持久化事务提交；近实时搜索存在短暂可见延迟。搜索系统还应把数据库作为事实源，索引作为可重建投影，避免把一次搜索未命中误判为业务数据不存在。

### 自测与参考答案

## 相关性为何不只看热度

来源标识：generated.course.12015.lesson.32152

### 相关性排序解决什么问题

依据课程目录编写的AI生成学习资料，非原授课逐字稿。搜索“Redis Lua”时，用户首先期待标题和正文真正讲 Redis Lua 的课程，而不是平台上最热门但主题无关的 Java 课程。相关性排序衡量查询与文档文本的匹配程度，热度则反映浏览、收藏或学习人数。两者可以结合，但含义不同。合理策略通常让文本匹配决定候选与主要顺序，再用受限热度处理相近得分，避免热门内容长期垄断曝光，也避免冷门但精准的课程沉底。

### BM25 的直观机制

BM25 会考虑词项在当前文档中的出现情况、词项在整个集合中的稀有程度以及字段长度归一化。一个在少数课程中出现的专业词通常比“入门”这类常见词更有区分力；同一词出现多次会提高信号，但收益逐渐变小，不会无限线性增加；很长的正文天然包含更多词，因此需要长度校正。多字段查询还能给标题更高权重，例如 title^3 加 description，让标题精确命中的课程优先，同时保留正文召回。

### 受控加入热度的示例

设精准课程文本得分 8、热度 20，泛化热门课程文本得分 2、热度 10000。若直接把热度相加，热门课程会轻易反超。可将热度先做 log1p 或饱和函数，再乘一个较小系数，例如 final = textScore + 0.2 × log1p(popularity)。还可以只对文本已达到最低匹配门槛的候选加热度，或用 rank_feature 的饱和方式控制上限。离线评测时固定查询集合和期望结果，比较调整前后的前几名，而不是凭单个案例猜测。

### 常见误区与业务边界

热度不是质量的绝对证明，它受课程上线时间、营销和历史曝光影响。仅按销量排序会把搜索变成榜单；完全不用行为信号又可能无法区分文本近似的课程。权重不能只看最终总分，还要用 explain 拆解文本、字段提升和函数得分。过滤条件如“已上架”“用户可访问”应放在过滤语义中，不参与相关性竞争。排序实验要防止未来信息泄漏，并关注零结果率、点击质量和长尾课程曝光，而不是只优化总体点击率。
