## 变量和方法怎样配合

来源标识：generated.course.12001.lesson.32011

### 概念入门与课程主题

来源声明：本资料依据课程目录编写，是 AI 生成学习资料，非原授课逐字稿。Java 编程基础关注如何把输入转成明确的计算结果。变量保存某一时刻的数据，类型限定数据能表示什么以及可执行哪些操作；方法把一段具有名称、输入和输出的逻辑封装起来。二者配合后，调用者准备实参，方法通过形参接收，在局部变量中完成计算，并用返回值交回结果。

### 作用域与调用机制

局部变量只在声明它的代码块内可见，方法参数的作用域是整个方法体。Java 采用值传递：基本类型传递数值副本，引用类型传递引用值的副本。重新给参数赋值不会改变调用者变量本身，但通过引用访问同一个可变对象可能改变对象状态。方法签名由名称和参数类型序列确定，返回类型不参与重载判断。清晰的方法应只承担一个容易命名的职责。

### 可手推示例

编写 static BigDecimal calculateTotal(BigDecimal unitPrice, int quantity)。先检查单价非空且不为负、数量大于零，再定义 subtotal=unitPrice.multiply(BigDecimal.valueOf(quantity))，最后返回 subtotal.setScale(2, RoundingMode.HALF_UP)。调用 calculateTotal(new BigDecimal("19.90"), 3) 时，unitPrice 与 quantity 是参数，subtotal 是局部变量，返回结果为 59.70。金额用 BigDecimal 可避免 double 的二进制精度误差。

### 常见误区与边界

局部变量在使用前必须明确赋值，不能假设它自动为零。不要用 == 比较字符串内容，应使用 equals；BigDecimal 业务比较通常使用 compareTo。一个方法里同时读取输入、改数据库、计算价格和发送消息会难以测试，应拆成不同职责。参数过多常提示缺少一个有意义的对象。命名应表达业务含义，如 unitPrice 而不是 a。输入校验的位置要统一，避免同一规则在各处不一致。

## 对象如何表达业务职责

来源标识：generated.course.12001.lesson.32012

### 概念入门与课程主题

来源声明：本资料依据课程目录编写，是 AI 生成学习资料，非原授课逐字稿。对象把相关数据与行为组织成一个有边界的业务概念。相比只保存字段的“数据袋”，具有职责的对象会保护自身状态并提供有业务含义的方法，例如 Order.pay()、Order.cancel()。本课通过封装、构造约束和协作关系，让代码中的名称与真实业务语言对应，使规则更集中、更容易测试。

### 封装与职责机制

字段通常设为 private，外部通过构造方法或业务方法影响对象。构造时建立必需的不变量，例如订单号非空、金额非负；状态变化则由方法检查当前状态是否允许。对象不应因为方便就负责所有事情：订单可判断能否支付，但支付网关调用由应用服务协调。值对象适合表达金额、地址等按值判断相等且通常不可变的概念，实体则通过稳定标识保持身份。

### 可执行示例

定义 Order，包含 id、amount、status。构造新订单时状态固定为 PENDING。pay() 先要求当前状态为 PENDING，再改为 PAID；cancel() 允许 PENDING 变为 CANCELLED，但拒绝已支付订单。应用服务先加载 Order，调用 pay()，然后保存，再发布支付完成事件。单元测试直接创建对象并验证 PENDING 能支付、PAID 不能再次支付，不需要启动数据库或 Spring 容器。

### 常见误区与边界

给每个字段生成 setter 会绕过业务规则，例如调用者可直接把订单从 CANCELLED 改成 PAID。另一方面，封装不等于把所有逻辑塞进一个巨型对象；跨多个聚合、外部服务或事务流程仍应由应用服务协调。实体的 equals 和 hashCode 设计要谨慎，持久化前后标识变化可能影响集合行为。DTO 用于边界传输，不应替代领域对象长期承载规则。

### 自测与参考答案

自测一：为什么用 pay() 比 setStatus(PAID) 更好？参考答案：方法名称表达意图，并能集中校验合法状态转换。自测二：调用支付平台属于订单对象职责吗？参考答案：通常不是，应由应用服务协调外部接口与订单状态。自测三：什么是不变量？参考答案：对象从创建到每次合法操作后都必须成立的规则，例如金额不能为负。测试应针对允许与拒绝的状态路径分别断言。
